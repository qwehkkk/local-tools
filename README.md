# 本地工具（local-tools）

在浏览器里本地运行的工具集。**文件不上传、断网可用**，这是产品定位，不是营销话术——代码里没有任何把文件发出去的调用。

当前状态：**3 个工具已可用**，均通过端到端验证。前两个工具首屏下载 **0 字节**；第三个按需加载 511KB 的 PDF 引擎（打开页面不下载）。
- 工具一「本地脱敏」：支持导出映射表 + 随时还原。
- 工具二「本地图片压缩」：批量压缩、转 WebP、指定目标体积、打包成 ZIP 下载。
- 工具三「本地 PDF 拆合」：合并、拆页、按页码范围抽页，结果打包 ZIP。上传字节恒为 0。

2. 入口调 `installNetCounter()`
3. 复用 `.pane` / `.bar` / `.card` / `.note` 结构，不要另起一套样式
4. 纯逻辑（解析、校验、命名）单独拆成 `assets/<x>.js`，这样能进 `npm test`
5. 写一个 `verify-<name>.mjs`，断言必须落在**磁盘产物**上，不能只看页面自己报的数字
6. 首页加一张 `.card`

## 为什么用规则引擎，不用大模型

Phase 0 实测过浏览器端跑 LLM（见 `../Phase0-实测报告.md`），结论是**能做但不必用在这**：

- 中国 PII 的主体是结构化的：身份证有校验位、银行卡有 Luhn、手机号有固定段。正则的准确率比模型高，而且**可解释、可测试、可穷举**。
- 模型识别「110101199003078515」这种号码并不比正则可靠，还会编造。
- **首屏下载从 120MB 变成 0 字节**——这直接绕开了 B 路线最大的风险项。

所以顺序调整为：规则引擎先上，NER 只作为「人名/机构名」的可选增强，后置到第二个版本。

## 规则引擎设计

`assets/pii-rules.js` 是纯函数模块，浏览器和 Node 都能直接跑。

三条原则：

1. **宁可少报，不可误报。** 弱特征规则必须带校验位或上下文关键词才能命中。裸人名不识别——强行识别会把「王小明今天开会」里的正常词汇全标黄，用户会立刻不信任这个工具。
2. **冲突消解有顺序。** 校验通过 > 规则优先级 > 匹配更长。18 位数字同时满足身份证和银行卡格式时，优先判身份证。
3. **隐私工具宁可多遮。** 身份证校验位不通过时**仍然遮盖**，只是降低优先级并在 UI 上标「未通过校验，建议人工确认」——用户手抄错一位也该被保护。

### 加一条规则

```js
{
  id: 'my_rule',
  label: '显示名',
  severity: 'high' | 'medium',
  regex: /.../g,
  boundary: 'digit' | 'alnum' | 'none',  // 前后不能是数字/字母数字
  priority: 80,                           // 越大越优先
  captureGroup: 1,                        // 可选：只取捕获组
  validate: (raw, text, start, end) => true,
  validOnly: true,                        // true = 校验不过就丢弃
}
```

加完记得在 `tests/rules.test.mjs` 补两条用例：**该命中的**、**不该命中但长得像的**。

## 隐私承诺怎么做到「可验证」

口头承诺没用。页面右上角有个计数器，显示**本页脚本实际发出的网络请求次数**（PDF 工具显示**向外发送的字节数**），实现方式是直接接管 `fetch`、`XMLHttpRequest`、`sendBeacon`、`WebSocket`，并对非 GET 请求统计 body 大小。

任何人按 F12 → Network 面板，粘贴内容或拖入文件，都会看到没有任何一条请求携带他们的文件。这是目前竞品基本没做好的地方，也是这些工具最硬的信任凭证。

**一条踩过的坑**：工具三用 `import()` 懒加载 PDF 引擎，而 `import()` 不经过 `fetch`／`XHR`，计数器抓不到。于是徽章会显示「0 请求」，但 Network 面板里明明有一条 511KB —— 这种自证等于骗人。所以那个页面改报**上传字节（恒为 0）**，并单独显示引擎的真实体积。**任何新工具都必须让徽章说的是真话**，宁可数字难看，也不能让它变成安慰剂。

**新增代码时必须守住这条**：不引 CDN、不引外部字体、不加统计脚本。一旦加了，整个定位就塌了。第三方库只能像 `vendor/pdf-lib.esm.min.js` 这样自托管到 `assets/vendor/`。

## 映射表与还原（这个工具的差异点）

「部分保留」和「完全遮盖」是不可逆的——信息真的被丢掉了。「占位符」模式则把每个敏感值换成固定编号，同时生成一份映射表：

```
占位符,类型,原文,出现次数
〔姓名1〕,姓名,张伟,2
〔身份证号1〕,身份证号,110101199003078515,1
```

**三条必须守住的规则：**

1. **同一原文必须共用一个占位符。** 张伟在文中出现两次都是〔姓名1〕。如果编成〔姓名1〕〔姓名2〕，读者会以为是两个人，还原也会错。
2. **编号按类型独立递增。** 姓名从 1 开始，身份证号也从 1 开始，互不干扰。
3. **只认占位符模式。** 别在其它模式下宣传"可还原"，那是假的。

**还原的容错**：`〔姓名1〕`、`【姓名1】`、`[ 姓名1 ]` 都能识别。长占位符优先替换，避免〔姓名1〕抢掉〔姓名11〕的开头。还原不掉的占位符会明确报数，不假装成功。

**安全边界**：映射表本身就是最敏感的文件，页面上有红字警告。内存里的映射表在刷新后即消失，不写 localStorage、不写 IndexedDB——这是刻意的，不是没想到。

## 人名识别的坑（改这块之前先读）

中文人名没有形态特征，只能靠「字段名 + 值」。这条路上踩过的坑，都已经变成测试用例：

| 输入 | 期望 | 处理方式 |
|---|---|---|
| 联系人张伟负责后续 | 张伟 | 贪婪匹配会吃成「张伟负责」，靠停止词剥尾 |
| 王芳的助理 | 王芳 | 遇分界符（的/在/将…）截断 |
| 甲方指定联系人张伟 | 张伟 | 字段名后接动词不算值，负向前瞻排除 |
| 联系人为王芳 | 王芳 | 「为/是/系」是连接符，不是停止词 |
| 甲方为公司 | 不识别 | 取到的是机构词则丢弃 |
| 李小明先生 | 李小明 | 多字停止词优先，再考虑单字 |

**方向性判断：宁可漏遮，不可错遮。** 错遮会遮住正常词（「指定」被遮成〔姓名2〕），让用户立刻不信任工具；漏遮交由用户通读复核。所以停止词表偏保守。

## 工具二：图片压缩的五个决定

全部用浏览器原生的 `createImageBitmap` + `OffscreenCanvas`，**没有引入任何第三方库**。

**1. 不用 JSZip，自己拼 ZIP。** 图片本身已经是压缩格式，ZIP 里再 deflate 一遍收益接近 0，却要多背 100KB。`assets/zip.js` 只做 store 模式（不压缩），约 100 行。两个坑必须记住：
- 文件名要置 **UTF-8 标志位（bit 11）**，否则中文名解压后是乱码；
- 中央目录里的 **本地头偏移量** 必须精确累加，错一个字节整包就废。

验证方式不是"看起来能解压"，而是交给 `Python zipfile.testzip()` 逐条校验 CRC，再用 PIL 把每张产物读回来验证格式与像素尺寸。

**2. 串行处理，不并发。** 同时解 6 张大图很容易把内存顶爆，而串行的总耗时差别很小（单张 50–200ms）。每张处理完立刻 `bitmap.close()` 释放。

**3. 压不动就保留原图（默认开）。** 已经优化过的 WebP、极小的 PNG，转完可能更大。硬压会得到"压缩后体积翻倍"这种荒唐结果。

**4. 「按目标大小」不能反向膨胀。** 最初实现是二分搜索质量、逼近目标上限——结果 16.5KB 的图被"压"成 55KB，因为在不超过目标的前提下它尽力提高了质量。修法：**原图若已在目标体积内，就按质量设置压一次，更小才采用**。对压缩工具来说，"不超过原体积"比"逼近目标"更根本。

**5. 用 `imageOrientation: 'from-image'` 解码。** 手机拍的照片靠 EXIF 记录方向，不处理的话竖拍照片会躺倒。

**产物命名**：跟随输出格式改扩展名；批量下载时重名自动加 `-2`、`-3`，不会互相覆盖。

## 工具三：PDF 拆合的四个决定

这是唯一一个引入了第三方库的工具：**pdf-lib 1.17.1**，单文件 ESM，523,373 字节（511 KiB，gzip 后约 201 KB）。浏览器的原生 API 读不了 PDF 的对象结构，这件事绕不过去。

**1. 懒加载，打开页面仍然零下载。** `await import('.../pdf-lib.esm.min.js')` 放在第一次上传文件时，而不是模块顶部。所以首页和工具页首屏的下载量和工具一、二完全一样，511KB 只在真的要用时付。

**2. 徽章改报「上传字节」，不再报「请求次数」。** 这是被逼出来的：`import()` 不经过 `fetch`／`XMLHttpRequest`，计数器抓不到它，于是徽章会显示「0 请求」——但用户打开 Network 面板明明能看到那 511KB。**这种自证是骗人的。** 所以计数器增加了「向外发送字节数」统计（`fetch` 的 method+body、`XMLHttpRequest.send` 的 body），页面上同时显示引擎的真实体积。请求数可以不为 0，上传字节必须恒为 0。

**3. 加密 PDF 必须明确拒绝。** pdf-lib 遇到有密码保护的文件会抛 `EncryptedPDFError`。这里不 try/catch 后静默产出空文件，而是把那一行标红、禁用页码输入、排除出页数统计，点生成时提示「这份 PDF 加了密码，本工具不处理加密文件」。验证脚本会把加密样本一起传上去，确认它没有污染其它文件的处理。

**4. 页码解析与产出计划是纯函数。** `assets/pdf-range.js` 不碰 DOM 也不碰 pdf-lib，所以在 Node 里能直接测：`1,3-4,2` 去重保序、`5-` 到末尾、`9-12` 超出总页数、`3-1` 起点比终点大、拆分时跨文件不混页。15 条用例覆盖这些边界，界面层只负责把结果画出来。

**页序限制（如实写在页面上）**：只能按文件排序，文件内部保持原页序。不支持「把 A 的第 3 页插到 B 的第 1 页之前」——那需要全局页列表 UI，是另一个量级的工作。

**验证方式**：素材用 PIL 生成，**每页尺寸都不同**（595×842 / 500×500 / 400×600 …）。这样输出文件的 mediabox 序列就能反推出页序对不对，不用靠肉眼比对。产物一律交给 `pypdf` 独立解析（另一个实现的读取器），它若读不回来就说明 pdf-lib 写坏了结构。

## 已知局限（要如实告知用户，不要藏）

**共用**
1. **只吃纯文本 / 单张图片 / 标准 PDF**，不做 OCR、不做批量文件夹递归。
2. 不承诺「保证没有遗漏」，都是辅助工具。

**工具一 · 本地脱敏**
3. **裸人名不识别**。正文里随机出现的「王小明」不会标黄，只有带字段名才会。
4. **地址遮盖保留省市级**。太小城市仍可能定位到人。
5. Word / PDF 需要先复制成文本，或后续做解析器。

**工具二 · 本地图片压缩**
6. **HEIC / HEIF 不支持**（iPhone 默认格式）。浏览器的 `createImageBitmap` 解不了，会如实报错而不是静默跳过。
7. **GIF 只取第一帧**，动图会变成静态图。
8. **PNG 无损**，质量参数与「目标大小」对它无效，只能靠缩小边长。
9. **JPEG 无透明通道**，透明区域会填白（已铺白底，避免变黑）。
10. 单边超过 8000px 的图可能因内存不足失败。

**工具三 · 本地 PDF 拆合**
11. **加密 PDF 不支持**，会明确报错。
12. **不保留书签、目录、表单域、注释**；数字签名会失效。
13. **页序只能按文件排**，不能跨文件把单页插到任意位置。
14. **不做重新压缩**，输出体积接近原文件之和（拆合工具不该偷偷动内容）。
15. 单文件超过 200 MB 可能内存不足。

### 怎么发新版本

```bash
npm run verify:all     # 本地五套验证（发布前必跑）
git add -A && git commit -m "…"
git push               # 代理正常时直接推
npm run push           # 备选：git 协议不通时走 GitHub API
```

**两种推送方式**：`git push` 走的是 `github.com:443`，本机代理有时会拦（`CONNECT tunnel failed, response 502`）。
`npm run push`（`tools/push-via-api.mjs`）走 `api.github.com`，上传 blob → 建 tree/commit → 更新 ref，
效果等价、可用性更好，但远程 commit 的 SHA 与本地不同。用 API 推过之后，若换到别的机器继续开发，
先 `git fetch && git reset --hard origin/main` 对齐，否则 push 会被判成 non-fast-forward。
代理正常时优先用 `git push`，SHA 一致，省掉这个步骤。

- `npm run verify:live -- --url=https://tools.toolona.com/` 在真实证书校验下 34 项全绿。

**证书卡住不签怎么办**（这次踩到了，值得记）：

DNS 配好后 GitHub 一直不申请证书，把 Pages 的自定义域**置空再重新设回**即可重新排队：

```js
PUT /repos/{owner}/{repo}/pages  { "cname": null }
PUT /repos/{owner}/{repo}/pages  { "cname": "tools.toolona.com" }
```

等同于在 Settings → Pages 里删掉域名保存、再填回去。本次约 90 秒就签出来了。
副作用：GitHub 会自己提交两个 commit（`Delete CNAME` / `Create CNAME`），
且它写出的 CNAME 文件**没有结尾换行**，与你本地版本会有 1 字节差异 —— `git reset --hard origin/main` 对齐即可。

证书下来后再开强制 HTTPS（`https_enforced: true`），否则拿不到证书时开不了。

仓库根目录的 `CNAME` 文件（内容就是域名）不要删，删了自定义域会掉。

### 四条注意事项

1. **换域名必须用脚本，不要手改**：`npm run set-domain -- https://新域名[/子路径]`。
   它会重写四个页面的 `canonical`、重新生成 `sitemap.xml` 和 `robots.txt`（含 Sitemap 声明）。
   改完跑 `npm run verify:site`，会校验 canonical 是否自指、sitemap 是否覆盖全部页面。
2. **发布是整个目录上传，静态托管没有排除机制**。也就是说 `tests/`、`tools/*.mjs`、
   `README.md`、`package.json` 在线上是能访问到的。它们不含任何密钥或用户数据，
   但 `robots.txt` 已经把这些路径 Disallow 掉，避免被当成页面收录。
   `.dev/`（Chrome 配置、截图、素材）必须留在目录外，否则会连 cookie 一起传上去。
3. **首页只放真能用的工具**。占位的「开发中」卡片看起来完整，实际点不动，
   会让人以为整站没做完 —— 已验证脚本里有一条断言专门拦这个
   （`每张卡片都能点`：`.card` 总数必须等于 `.card[href]` 数量）。
4. `assets/vendor/pdf-lib.esm.min.js` 是**手工 vendor 的第三方文件**，不是构建产物。更新方式是：
   ```bash
   mkdir -p /tmp/vendor && cd /tmp/vendor && npm i --ignore-scripts pdf-lib
   cp node_modules/pdf-lib/dist/pdf-lib.esm.min.js <repo>/assets/vendor/
   # 删掉最后一行的 sourceMappingURL 注释，避免 devtools 去请求不存在的 .map
   ```
   当前版本 **1.17.1**，523,373 字节。升级后必须重跑 `npm run verify:pdf`。
